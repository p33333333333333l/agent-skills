# 按项目自己的约定整理目录

最后更新：2026-11-17

通用整理器会失败，因为它拿自己的模板去套项目。这个技能反过来：先读项目写下的布局规则，再拿 `git ls-files` 的真实结果去比，差集就是该动的地方。

**没写规则的项目，只报事实、不猜结构。** 猜出来的目标结构一定会和项目里已有的惯例打架。

## 两个脚本

都在本 SKILL.md 同目录的 `scripts/` 下，纯标准库 Python 3，无依赖。

| 脚本 | 作用 | 会不会改文件 |
|---|---|---|
| `inventory.py` | 读 git 索引 + 声明文档，报事实与漂移 | 不会 |
| `move.py` | 按计划 JSON 搬文件、改引用、跑验证 | 加 `--apply` 才改 |

改过脚本后跑 `bash tests/make-fixtures.sh <临时目录>` 生成两个夹具仓库自检，别拿用户的真仓库试。

## 步骤

### 1. 盘点（只读）

```bash
python3 <本目录>/scripts/inventory.py <repo>
```

加 `--json` 拿结构化结果。输出段落按重要性排：声明文档 → **DRIFT** → 各区文件数 → 扩展名 → 根目录文件 → 被跟踪的产物 → 磁盘上被忽略的目录 → 超大文件 → 超长行 → 无引用源文件 → 重名文件。

完成判据：脚本退出码 0，且你能贴出它的 `## DRIFT` 原文。再读取各目录内实际存在的布局声明（含嵌套 `AGENTS.md`），核对列出的文件和真实清单；DRIFT 只检查区名，不能据此断言所有文档一致。

### 2. 判读：只认这五类问题

按顺序看，前四类是可直接动手的，第五类只报告。

1. **ABSENT**：文档声明了某个区，仓库里没有。可能是文档过期，也可能目录被误删。先问是哪一个，别直接建空目录，也别为消除 ABSENT 把无关文件搬进去。
2. **未命名区**：顶层有实际内容（被跟踪文件 ≥2 个），文档里一个字没提。这是最常见的真问题——要么补文档，要么搬走。
3. **根目录散落**：根目录有项目已有的区能容纳的文件。根目录该有的只有：构建/工具配置、入口文档（README/AGENTS/SCHEMA 之类）、许可证、`.gitignore`。
4. **被跟踪的产物**：`tracked but generated` 里列出的，`git rm --cached` 加进 `.gitignore`，不搬。取消跟踪也是改动，和搬移一起进步骤 3 的表格等确认。
5. **无引用源文件、重名文件**：只报给用户，不据此搬。脚本看不见的语言（`.astro`、`.vue`、`.svelte` 里的 import，框架按位置加载的约定文件）都会误报成孤儿。

判断细节、各语言陷阱、哪些「看起来乱」其实不该动，见 [references/judgement.md](references/judgement.md)。

完成判据：五类问题各写一行「有 / 无」；写「有」的必须指回盘点输出的具体行，指不回去的划掉。

### 3. 出计划，等确认

🔴 **CHECKPOINT**：把计划写成表格给用户看，等明确同意再执行。表头固定五列：

| 从 | 到 | 为什么（引用盘点里的行） | 引用要改的文件数 | 风险 |

- 「为什么」须引用盘点事实与项目约定。选择目标前读文件的用途和实际调用方；被应用导入的业务模块不能仅因名字像脚本就放入维护脚本区。
- 一次计划只处理一个主题（比如「把 3 个散落的脚本收进 scripts/」），不要一次搬二十个文件。
- 用户说「你看着办」也算确认，但仍要把表列出来，让他有机会否掉。
- 计划里同时列出「搬完要改哪份声明文档的哪一段」，一并等确认——改文档也是改动，不能搬完再自作主张补。
- 用户否掉某一条：只把该条移出计划，其余照原样执行，不要重新生成整份计划。

完成判据：用户对这张表给出了明确答复（同意 / 否掉哪几条 / 让你看着办）。

### 4. 执行

计划 JSON 格式与字段含义见 [references/plan-format.md](references/plan-format.md)。先空跑一遍：

```bash
python3 <本目录>/scripts/move.py plan.json          # 只打印将要改的引用，不落盘
python3 <本目录>/scripts/move.py plan.json --apply  # 真改
```

`--apply` 会拒绝：工作区脏（退出码 3）、改扩展名、源不存在、目标已存在、两个搬移抢同一个目标（退出码 2）。这些都是对的，别加 `--allow-dirty` 绕过——脏工作区里回滚会连用户的改动一起毁掉。

完成判据：退出码 0，`git status --short` 与计划中的搬移和引用改写一致。退出码 3 表示写入前发现已有改动：保留现场，先处理这些改动，不能执行回滚。退出码 4 表示本轮验证失败，按下面的回滚条件处理。

### 5. 验收

```bash
git -C <repo> status --short                    # 应是 R（重命名）+ 若干 M
git -C <repo> diff --stat
```

再逐条核对，每条都要有命令和输出：

| 检查 | 命令 |
|---|---|
| verify 过了吗 | 计划里的 `verify` 原样跑（`npm run test` / `pytest -q` / `npm run build`）。项目没有测试就写 typecheck 或 build；连这个都没有，写 `--no-verify` 并在汇报里说明「没有自动验收，只验证了引用改写」。`--no-verify` 是最后手段，不要拿它跳过项目本来就有的测试 |
| 声明文档跟上了吗 | `git -C <repo> diff --stat -- AGENTS.md CLAUDE.md SCHEMA.md README.md docs/` — 搬了目录就必须更新结构段，这是核心交付，不是可选项 |
| 有没有残留引用 | 检查 `move.py --apply` 的 `WARNING: old paths still referenced` 输出，并用 `git grep -n -F -- '<旧路径>'` 逐条复查旧路径；命中时区分真实引用与历史说明，真实引用必须补改 |
| 改动到底几项 | `git -C <repo> status --short \| wc -l` 和 `git -C <repo> ls-files \| grep -c '^[^/]*$'`（根目录文件数） |

**数字自检（硬要求）**：汇报里出现的每个计数——改动项数、根目录文件数、子目录数、引用处数、某个区有多少文件——都必须能贴出产出它的那条命令。贴不出命令的数字删掉，不要凭印象写。同一份报告里两处数字互相矛盾，比数字写错更糟。

汇报给用户：搬了什么、引用改了几处、verify 结果、文档改了哪段、怎么回滚。

回滚前确认：执行前工作区干净，且执行后没有用户或其他进程新增改动；否则停下逐项处理，不运行整体回滚。满足条件且未提交时用 `git restore --staged --worktree . && git clean -fd`。这条会把搬移、引用改写、`git rm --cached` 全部还原，同时删掉本轮新建的 `.gitignore` 之类未跟踪文件（这正是「回到动手前」的意思）；被 gitignore 的产物（`__pycache__`、`node_modules`）留在磁盘上不动。已提交时由用户确认后再 `git reset --hard <搬移前的提交>`——这条会丢工作区改动，不要自行执行。

## 失败模式

| 症状 | 处理 |
|---|---|
| 文档没写任何布局规则 | 只报事实。可以提议补一份 `AGENTS.md` 结构段，但别自作主张搬文件。 |
| 声明区判成 ABSENT，但目录确实在 | 目录可能被 gitignore 了。脚本已查磁盘，仍报 ABSENT 就是真的没有；去问用户，别建空壳。 |
| 无引用列表里出现 `content.config.ts`、`robots.txt.ts`、`middleware.ts` 这类 | 框架按位置加载，属误报。跳过。 |
| verify 失败 | 先按上文确认整体回滚条件；满足才按脚本打印的命令回滚，再查漏改的引用并重跑。不满足就保留现场逐项处理。 |
| 项目是纯文档/纯数据仓库 | 没有源文件就没有引用可改，搬移退化成 `git mv`。仍按步骤 1–5 走，但把 `verify` 设为空。 |
| 目录里混着 gitignore 的产物（`__pycache__`、`node_modules`） | 不搬、不删，只确认 `.gitignore` 覆盖了它。磁盘上的产物不是目录问题。 |
| 用户要的是「重构代码」而不是「整理目录」 | 停下说明：本技能只改文件位置，不改代码结构。 |
| 盘点输出上万行、或跑超过 30 秒 | 先加 `--json` 取结构化结果，只对「≥2 个跟踪文件且文档没提」的区展开。大区（几千文件的 `data/`、`raw/`）只记数量，不逐条读。 |
| `inventory.py` 报错、或目录不是 git 仓库 | 停手报告。不要用 `find`、`ls -R` 拼一份替代盘点——没有 git 索引就分不清「被跟踪」和「本地产物」，结论会错。 |
| 用户否掉了计划里的某一条 | 只把该条移出，其余照原样执行；不要重新生成整份计划，也不要顺手改动被否的那块。 |

## 不做什么

- 不删文件。产物只用 `git rm --cached` 取消跟踪，禁止用 `git rm` 删除工作区副本；其他要删的只列出来，让用户决定。
- 不改依赖、不动 `package.json` 的 `exports`、不合并模块。
- 不按「社区最佳实践」造结构。只认项目自己写下的规则。
- 不为了凑出「整齐的结构」新建空目录。ABSENT 先问是文档过期还是目录被删。
- 一次不搬超过一个主题的文件。大改先拆成多轮，每轮独立验收。
