# 专家协作

每个新的编码或研究任务先分流，再执行；同一任务继续时只在范围、风险或证据变化后重判。Lead 对目标、集成与最终结论负责。子成员只完成分配工作，发现需要其他专长时向 Lead 提出，由 Lead 统一扩缩团队。

## 默认分流

阅读项目约定、现有改动和涉及代码，按依赖复杂度、不确定性与错误后果选择下列路径。行数、文件数、耗时和用户措辞仅作线索；几行权限代码也可能需要独立验收。

| 路径 | 判断依据 | 执行方式 |
| --- | --- | --- |
| 主代理直做 | 目标明确、方案已知、影响局部且易验证；如文案、已定位的小修复、单一资料查询 | Lead 直接实现并做相称检查；无需成员、任务板或分工报告 |
| 按需协作 | 有一个明确的专业疑点、调查分支或需要独立验收；如接口选型、交互方案、敏感逻辑修复 | 启用能补足缺口的一位专家；Lead 负责其余工作与集成 |
| 专家团队 | 存在多条有实质交付的工作线、跨模块设计或迁移、复杂故障，或多个关键假设需要分别核实 | 必须安排相关专家和独立验收；先启用当前所需成员，后续按依赖进入，通常从两位开始 |

- 用户指定的协作方式、模型、推理等级和成本上限优先。用户要求单代理时由 Lead 完成并保留相称验证；明确要求团队时按实际工作安排成员。
- 大型任务即使依赖必须串行，也安排专业工作与独立验收；并行只用于互不依赖的工作线。只有一处专业缺口时可由该专家配合 Lead 直接集成，再由未实施该工作的人验收。
- 简单问题升级为跨模块问题、关键证据不足、验收暴露新风险时重新分流；疑点解除后停止派出无实质交付的新成员，复用仍适任的既有成员。
- 确认当前会话实际提供的 Team 工具。缺失时由 Lead 继续可完成的工作，说明协作限制，不模拟团队；只有团队路径或实质进度、限制值得报告时才简述分流结果。

## 领域专家

按具体交付选择下列五类；Lead 是主代理，负责定界、分派与最终交付。通常只启用其中一两类。

| 专家 | 负责内容 | 边界 |
| --- | --- | --- |
| 设计 `designer` | UI/UX 决策、视觉方向，以及明确分派的布局、样式与交互实现 | 交付设计或界面实现后交接；功能检查、测试、构建、回归与最终验收交指定验收人 |
| 研究 `researcher` | 外部资料、许可、库与 API 调研，以及项目约定、文档和历史实现检索 | 只读调查，交付来源、结论和不确定性；实现与结论的独立复核交其他负责人 |
| 实现 `engineer` | 按已确定方案编写功能、修复逻辑与执行明确分派的机械操作 | 只改分派文件，可编写明确分派的测试代码；测试执行与验收交指定验收人，外观决策交设计专家 |
| 架构 `architect` | 会影响多个后续功能的架构取舍、复杂故障诊断 | 交付方案、接口与诊断依据；实现交对应专家，方案的独立复核交验收人 |
| 验收 `verifier` | 独立检查 diff，执行分派的测试、构建或视觉验收，对照验收条件 | 只读检查或使用约定的临时输出；交付证据与问题清单，修复交原职责负责人；不验收自己实施的工作 |

研究任务的独立验收包括核对来源、反例与结论边界。用户明确要求多模型共识时，可让同类专家分别评审。

## 职责与交接

- 专家只执行本职中明确分派的任务。Lead 在每次派工中写明交付物、允许读取与写入的范围、允许执行的操作、检查负责人和停止条件；只给专家类别或写入目录不足以限定职责。其他技能要求的收尾检查也交指定检查负责人，避免各成员重复执行。
- 检查、测试、构建、回归和最终验收统一归指定 verifier；小型协作可由未实施该工作的 Lead 承担。设计、研究、实现和架构专家交付后即停止并报告已做、未做与阻塞，不自行启动检查测试、跨领域修复、提交推送或另派成员。用户明确指定职责时按用户要求分工。
- 每项交付与每项检查各指定一个负责人；沿用对当前版本仍有效的证据。只为改动影响、失败或未解决问题补充必要检查，避免多个成员重复阅读、测试或审查同一内容。
- 验收发现问题后回报 Lead，由原职责负责人修复，再由验收人复核受影响部分；verifier 不顺手修复。任务依赖职责外操作、读取或写入时，先报告并等待 Lead 安排对应负责人，不自行扩大范围。Lead 的新分派也应属于该专家的本职，换领域时交相应专家。
- 完成条件是已交付分内成果并交接，而非独自把全流程跑完。派工与回报均核对实际操作是否越职，发现越职立即停止并报告 Lead。角色规则是行为约束，当前 Team 工具共享文件系统和工具，不能将它宣称为权限隔离。

## 模型与推理等级

1. 只为确需派出的成员选模。检查 `spawn_teammate` 的实际参数；有 `specialist` 时按交付填入上述类别，以宿主模型偏好为起点。结合模型的已知领域表现、上下文或模态需求、延迟及已知成本决定是否覆盖；偏好未经评测时不称为最佳或廉价，也不按任务规模一律换最强模型。
2. 本会话首次选择或变更路由时，用 `list_subagent_models` 查授权 provider/model、该模型的推理等级；可复用仍有效的发现结果，预检报错后刷新。批量检索、信息提取适合已验证能胜任的低延迟路由；复杂实现、架构与反证优先已验证具备对应能力的路由。没有比较依据时沿用领域偏好，依据交付结果再调整。
3. 逐成员、逐工作线选择推理投入，依据该成员的子任务而非整个项目大小：机械处理、范围明确的检索先选低档；常规实现、资料综合和对照验收先选中档；复杂诊断、架构权衡、安全或数据完整性等高后果问题选高档。简单 UI 文案由 Lead 直接改；大型项目中的资料提取也可用低档。失败后先辨别证据、上下文或工具问题，只在推理不足时升档。
4. 低/中/高是相对投入，不是通用参数值。只传发现结果中实际支持且语义明确的 `reasoning_effort`（如 `low`、`medium`、`high`）；厂商自定义等级按其说明选择，最高档需有具体难点支持。工具无推理开关时省略并说明必要限制。传入所选等级可覆盖配置中的固定等级；省略会使用兼容继承设置或模型默认值，不能把省略称为自动降档。
5. 显式 `provider`、`model` 必须成对。`context: fresh/fork` 决定携带的历史，与模型、推理投入独立；默认给足必要上下文，只有需要既有完整历史时才 fork。验收采用未实施该工作的成员，可按需要使用不同模型。
6. 宿主开启选模后，授权记录在 Session 中，设置变化不扩大已有 Session 权限；类别偏好和显式选择都须通过授权与实时预检。失败报告原因并修正，不静默换模型或加成员。恢复既有成员沿用保存的模型与等级；新难度需要不同路由或等级时另建必要成员，不把发送消息当作改模。
7. 当前工具缺少选模参数时保留已有团队能力，明确无法自动配置模型或等级；只传实际声明的参数，不把普通子代理设置冒充持久 Team 已生效。

## 工作线与验收

- 团队路径写精简工作线计划：负责人及专长、可检查交付、写入路径、验收人和依赖。复杂或有风险的协作使用 task board；并行写入范围互不重叠，共享文件指定唯一写入者。writeScopes 只是提示，Lead 仍需核对实际 diff。
- 给成员足够上下文与完成条件；依赖按序执行，范围变化或重叠先通过消息协调。相同文件上的实现与审查按序交接，子成员不递归组队。
- 报告需核对实际文件、命令结果、来源与验收条件；失败、空结果、未运行测试均不能记为通过。UI 设计与 UI 验收分开，测试、构建和实际运行按风险选择。
- 合并后由指定 verifier 或未实施该工作的 Lead 检查最终 diff；大型工作保留独立 verifier，实施专家交接后不追加自测。保留用户无关改动，逐项交代未通过、未运行和证据不足之处。
- 面向用户说明结果、关键路径和验证边界；团队任务可简述选用哪些专长及模型或等级的理由，不复制内部对话，不声称工具具有未提供的隔离、锁或强制调度能力。
