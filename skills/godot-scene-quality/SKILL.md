# Godot 3D 场景视听提质

把“哪里不对劲”收成有证据的问题，修复后证明哪里变好了。默认完成检查、可授权的小范围修复与结果汇报；用户要求只审查时保持只读。技能由相关任务触发，不是后台监控器。

## 1. 定界与保留意图

- 读取项目工作约定、进度和目标场景的设计说明，确认 Godot 版本、渲染器、运行入口、现有测试与 Git／协作规则。沿用项目工具和可复用资源。
- 优先采用用户指定的场景；未指定时检查当前任务涉及的 3D 场景，再无上下文才从项目主场景进入首个可玩的 3D 场景。开始时说明覆盖范围。全项目审查先列关卡及昼夜、交互前后等关键状态，逐项标记覆盖，不能用抽查代表全部。
- 确认美术方向、玩家尺度、可达路线，以及已认可或明确禁止改动的造型和超现实设定。风格相关参考按项目指针读取；不熟悉的真实物件交给调研者查照片、尺寸或工作原理，记录来源，图片不直接当作获授权资产。
- 涉及画面时，从已认可场景、设计说明及参考提取简短的**风格基线**：造型与细节密度、材质与纹理／像素尺度、色彩与明暗、预期焦点及空间疏密；标明来源和有意反差。缺记录时提出暂定基线供核对，不把个人偏好当既定方向；改变方向先确认。
- 涉及声音时，基线区分非场内配乐、场内声源与刻意异常，确认情绪、层次和静默意图；背景配乐不必有可见扬声器，已认可的穿墙声或延迟不强行写实化。
- 保留有记录的故意异常；无记录且可能承担叙事作用的异常列为待确认。其余部分仍检查结构和玩法合理性。低模、像素化、怪核或梦境不是制作缺陷的解释。
- 核对工作区与现存改动的归属；只修改本轮明确范围。共享道具、材质、着色器或脚本先查所有引用，确定影响的其他场景。

**完成条件**：检查范围、风格基线及其确定程度、保留项、写入负责人和运行／验收方式明确；现存用户工作有安全边界。

## 2. 取证与诊断

按 [场景检查表](references/checklist.md) 的对应分支检查，先取玩家实际遇到的视听证据，再查节点和数值。静态扫描只产出线索。

按目标选择画面、声音或联动分支，不把单项任务扩成全场视听翻修。

- 在隔离存档和设置的环境运行。记录场景、状态、相机位置／朝向／FOV、分辨率和渲染设置；为每个待修问题保存修改前视听证据。
- 画面问题至少查看玩家可达的整体视角和局部两个不同角度。运动看完整过程，通行或互动用真实玩家碰撞、输入和触发路径验证。
- **风格融合**：对照基线检查轮廓、细节、材质高光、图案尺度、色彩、光色与动画节奏，指出哪个因素在什么视角下显得异质、抢焦点或难辨。高面数、写实或鲜亮本身不是缺陷；没有证据时登记待证实线索，不先套用统一的降面数、降饱和或加雾方案。
- **视觉完整性**：沿玩家路线检查入口、转角、过渡和回望，覆盖近中远景、可见背面及会改变观感的关键状态；查临时灰盒、遗漏表面／材质、暴露边界、接缝收口、缺失的识别结构和局部密度失衡。结合设计意图区分未完成与刻意留白、简化或破损，不以填满空间作为完成标准。
- **声音层次与空间**：听实际游戏混音，查音乐遮盖提示、削波、循环接缝及转场突断；沿路线比较远近、朝向和遮挡，区分场内声源与非场内声音。逐层静音定位，不套统一响度、距离或全物理声学方案。
- **音画同步与状态**：同一时间线记录完整动作和可闻起音，分清动作相位、播放调用、素材前导静音与输出／录制延迟，先定位再修，不统一提前播放。覆盖双向动作、连续触发、暂停恢复、离开重进，查叠音、残留播放器／回调；保留有意跨房连续的音乐。
- 简短登记：`编号｜场景／节点或代码位置｜现象与影响｜证据路径／关键尺寸｜偏离哪条基线／是否刻意｜判断与置信度｜预期改进｜验收方法`。审美问题写出具体缺点及整体影响，而不是只写“丑”“高级感不足”。
- 分清三类：**已证实问题**、**待证实线索**、**已认可例外**。报错、日志和异常光斑先定位原因；不能仅凭命名、一个包围盒或个人偏好改动。
- 优先修阻断路线／交互、明显穿插／悬空／结构错误，再处理影响主要视角和路线观感的风格失配、完成度、比例、可读性、光照和构图。一次选择一组能完整修复、独立验证的高收益问题，通常不超过 3 项；剩余项保留在报告中，不宣称全部解决。

**完成条件**：每个待修项都有修改前证据、原因依据、影响范围和可执行的验收标准。没有证实的问题可以保持零修改。

## 3. 协作修复

编排者按当前会话实际可用的委派工具派发，展示一行工作线计划：基线、绝对目录／分支、负责人、允许修改的文件、验证负责人。依赖和单写者规则按项目执行。

- 按独立场景、道具或问题组拆分工作，每个独立设计工作组使用独立的 `designer` 子会话；调研、机械工作和验证分别交给对应角色。每份委派只携带该组需要的背景、保留项和证据，保持上下文干净；单个不可分割的小设计问题可由一个设计会话完成。
- 同一组的实施和视听纠错留在原设计会话；新工作组另开会话。并行写入只用于互不重叠且已隔离的范围，共享资源由唯一负责人串行处理，编排者协调依赖并集成。

| 工作 | 负责人及边界 |
| --- | --- |
| 场景、模型、几何、比例、摆放、材质、灯光、色彩、动画、外观生成代码，以及选曲、音色、混音、空间听感与动作节奏 | 对应 `designer` 拥有设计、亲自实施和后续视听修正；提供证据、保留项和验收标准，不转交其方案。 |
| 资料、代码关系和陌生引擎 API 调研 | `explorer` 只读查证，回报路径或来源及未知项。 |
| 不改变设计意图的精确机械操作或目标明确的非视觉播放、去重、生命周期逻辑 | 编排者处理小改动；明确操作及无需视听设计判断的理由后，才可交 `fixer`。 |
| 影响长期结构的取舍，或两轮修复仍失败的诊断 | `oracle` 给出取舍或诊断策略；不是每轮必经审查。 |
| 回归检查的编写与执行、截图／录像、试听及最终接收 | 编排者或独立非设计验证者；不交本轮 `designer`，设计预览不算独立验收。 |

- 已获“检查并改进”授权时，自动实施有证据、可回滚且符合现有方向的局部修复。新增玩法、重构全局系统、改变已认可的艺术方向、删除主要内容或推翻刻意异常，先说明影响并请用户决定。
- 保持最小完整改动，复用项目已有模型和辅助 API；可调参数遵循项目 Inspector 约定。避免为了增加细节而堆模型、换一套美术或新增审计框架。
- 风格与完成度修复以融入整体为目标，先处理已定位的失配因素或可见缺口；不为单件道具精致而提高全场复杂度，也不靠改验收镜头、压暗或遮挡藏住缺陷。统一的是视觉语言和完成标准，不是消除所有差异；保留已认可的异质焦点及其与周围环境的关系。
- 设计者不可用时报告设计实施阻塞，编排者和机械实现者不接管其视听设计。已完成的检查仍可交付。

**完成条件**：每项修改对应已登记的问题，保留项未被改写，实际 diff 没有越界；实施者交回精确路径和未验证项。

## 4. 独立对照验收

收回写入权后，由验证负责人检查实际文件与 diff，再运行检查：

1. 按项目要求做资源导入、解析／启动检查和受影响专项。可量化的几何、碰撞或状态错误补小型维护断言／回归检查；跨公共系统时才做相应组合检查，合并所有写入后运行一次。
2. 涉及画面时用真实渲染器，在与修改前相同的镜头、时间／状态和画质下重拍整体及两个局部角度；动态问题核对完整过程。以玩家正常视角为主，调试视角补充；回查入口、转角、回望与关键状态，以及相邻物件、共享资源场景和受影响路线。
3. 画面分别核对**原问题消失、整体融合、可见范围完整**：道具仍可辨认，轮廓与焦点清楚；无意失配已收敛，背面、边界及过渡无新缺口；认可反差、留白和氛围未被削弱。局部更漂亮但整体更突兀不能通过；测试、面数或灯光数量不证明更美观。
4. 声音按项目约定核对实际引用资源与导入结果；固定监听音量、输出与游戏设置，对照修改前后实际混音及必要的有声录屏，复听完整循环、动作和切场，检查邻接声源及分类音量控制。日志、波形、原始文件试听或静音启动均不能单独证明听感或同步合格；取不到实际混音或无试听能力时，列为听觉验收阻塞／待人耳复听。
5. 失败时把图像／录音／时间点及预期结果送回原实施者；视听设计归原 `designer`、机械逻辑归原实现会话修正，再独立复查。两轮未改善则暂停补丁、重新诊断；仍失败或缺证据的项保持未完成。

自动运行沿用项目指定的无窗口／虚拟渲染入口；本机若有 `$HOME/.local/bin/opencode-godot-test`，按其契约使用并隔离运行数据。真实画面检查不能由无渲染的 headless 成功替代。缺少渲染条件、场景加载失败或无法隔离存档时，明确报告阻塞和未验收范围，不直接打开会抢鼠标的桌面窗口。

**完成条件**：每个“已修复”项有相应前后证据、通过的回归及无邻接退化的检查；画面与声音分开记验收结论。按项目约定同步设计／进度说明。

## 5. 汇报

用用户能理解的语言简报：

- **检查了什么**：场景、关键状态及覆盖边界。
- **已改善**：现象 → 改动 → 实际结果，附路径和前后视听／检查证据；区分技术修复与审美判断，说明本轮涉及的风格、完整性或听感／同步变化，未检查项不记为通过。
- **保留／待定**：有意异常、尚未证实的问题、需要拍板的方向和本轮未处理项。
- **如何复看**：在编辑器或游戏中的位置、相关 Inspector 参数及最短验收步骤。
- **未验证与风险**：遗漏的状态、无法完成的检查、共享资源影响和仍需真人确认的观感／听感／手感。没有改善时如实报告，不凑修改数量。

## 维护本技能

修改本技能时，用 [维护情境](tests/scenarios.md) 检查分流、证据与停止条件；这些情境是行为验收案例，不是已经执行过的 Godot 测试。
