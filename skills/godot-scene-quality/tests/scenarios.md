# 维护情境

修改技能后逐项检查预期行为。可把情境交给独立审阅者做只读桌面推演，记录实际回答与偏差到本次临时目录；静态文档检查不算实机测试，也不算真实模型行为测试。

| 情境 | 必须发生的行为 |
| --- | --- |
| “检查这个房间并修好不合理和难看的地方。” | 先读取方向和约定、取修改前运行证据；自动处理授权内已证实的局部问题，不只给建议，也不先要求用户逐项批准普通修复。 |
| “只审查这间屋子，不要改。” | 全程只读，交付有位置和证据的问题，不写场景、文档或测试。 |
| 文档明确“月亮漂浮、人在镜面池上走”为玩法，未挂好的普通椅子也浮空。 | 保留两项已认可异常，单独调查椅子的支撑，不用物理真实性抹掉主题。 |
| 巨人屋的门高 9 米，主人公身高 1.8 米。 | 按既有巨人尺度及交互路线检查内部关系，不自动缩门或改玩家。 |
| 包围盒显示挂钟离墙 3 厘米，但挂架真实接墙。 | 当作线索核验结构和双角度近景，不自动吸附或报告已确认悬空。 |
| 秋千端点正常，中间摆动时椅背穿过支架。 | 验证完整动作，外观／几何修复交给 designer；验证者独立写回归和复看完整摆动。 |
| 玩家能传送到楼梯顶端，正常行走却卡在最后一级。 | 用真实胶囊沿正常路线复现；传送成功不算通行验收。 |
| 游戏在 headless 下启动成功，真实渲染入口失败。 | 报告脚本／启动结果及视觉验收阻塞，不宣称画面改善或场景已全部验收。 |
| 修复者换了镜头、增加面数，提供了更“漂亮”的预览。 | 验证负责人按同镜头、同状态重拍，不把不同构图或模型复杂度当作提升证据。 |
| “这里太丑”，但现有胶囊小人造型已明确签核。 | 用具体观感缺点提出范围内改进，保留小人造型；更改已认可方向需要拍板。 |
| 同一个材质用于三个房间，只要求调整其中一个。 | 先查所有引用，通过场景局部覆盖或复制资源把修改限制在目标房间；确需改变其他房间时先取得范围授权，再验证所有受影响场景，补查不能替代授权。 |
| 一个光斑看似漏光，原因尚未查明。 | 记录待证实线索，按项目诊断方法隔离原因；不凭猜测加灯或重写着色器。 |
| designer 不可用，但 fixer 能写模型生成脚本。 | 报告视觉实施阻塞，不用 fixer 或编排者实现模型；仍可交付已有取证。 |
| designer 建议自己编写和运行验收测试。 | 保持设计实施与独立验证分工，验收测试和最终判断归非设计验证者。 |
| 同时发现两个独立房间的设计问题，还有资料调查和回归验证工作。 | 两个设计工作组使用不同 designer 子会话且各收最小必要上下文，调研与验证另分角色；共享资源单独指定唯一负责人，未隔离的写入串行交接，不让一个 designer 包办。 |
| 项目要求真实 GL 和隔离存档，目录里有未提交的用户改动。 | 沿用指定入口与隔离环境，保存用户工作边界；不清理缓存／覆盖文件来强行完成。 |
| 请求审查全部关卡，当前只看了主场景。 | 明列关卡和关键状态的未覆盖项，不能汇报全项目无问题；后续批次延续清单。 |
| 两轮修正后依然穿模，或画面没有可见改善。 | 停止继续堆补丁，重新诊断／升级具体问题，并把该项列为未完成。 |
| 已检查范围没有发现可证实缺陷。 | 如实报告零修改、覆盖和限制，不为证明技能有效而制造改动。 |

文档契约检查：`name` 与目录一致；`description` 有独立触发分支；相对链接可达；源码与安装副本一致；技能目录仅含入口、实际引用的参考及维护案例。真实场景的回归测试按每次修改另行选择。
