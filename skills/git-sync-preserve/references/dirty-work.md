# 脏工作与冲突分支

仅在入口发现暂存、未暂存或未跟踪工作时读取；恢复冲突也在这里处理。
最后更新：2026-11-14

本文件不扩展入口的适用范围。入口适用门未通过时，A 节只读快照可供上位流程复用；B–E 的 stash、清理、merge、恢复与推送衔接仅用于已通过适用门的同步任务，不能据此在 main 上操作或跳过 rebase／PR。

## A. 静止状态的完整证据

先协调编辑器／生成器暂停写入。快照在仓库外私有目录，路径清单用 NUL 分隔，处理空格、换行、点文件和符号链接；不得跟随链接把外部目标当成本地文件。
保存并核验：

1. HEAD、main、远端固定 OID；原始 index 文件和必要的索引对象、`git ls-files --stage -z` 的路径／stage／mode／blob 映射；记录原索引是否为空差异。
2. `git diff --binary --full-index --no-ext-diff --no-textconv` 与同参数的 `--cached` 输出。它们用于证据和比对，**不是完整文件备份**。
3. 所有本地变更涉及路径的完整原始文件，包括二进制；已删除路径保存“原来缺失”，而不是补回旧文件。保存类型、可执行位／模式、链接本身和链接目标文本、重命名两端；若依赖 ACL／扩展属性等额外语义，必须用支持它们的方式保存并验证，否则停止。
4. 全部未跟踪内容（含点文件、链接、空目录及目录模式）；用 `git ls-files --others --exclude-standard -z` 加不跟随链接的目录遍历交叉核对。嵌套仓库不能当普通未跟踪目录打包后就声称已保存其 Git 状态。
5. 原 stash 清单的固定 OID 和顺序、状态清单，以及每个文件／链接的内容哈希与 mode／类型清单；原始索引字节另算哈希。

从备份实际读回所有文件与链接，比较哈希、类型、模式、缺失记录和路径全集；不能只检查压缩包存在或 diff 非空。
在写入者静止时再次对照 live 清单，任何变化都重新取快照；空间不足、读回失败或权限缺失即停，尚未清理 live 文件。
原始 index 仅作证据／灾难恢复材料，合并后不能直接把旧 index 覆盖回新 HEAD。
忽略文件默认留在原处，不执行 `stash -a` 或 clean；识别上游写入路径及目录／文件类型碰撞，可能覆盖 ignored 内容时先专项保护并验证，做不到就停。

完成条件：每项原工作都有可读回的独立副本，索引／工作树两个层次可重建，能力范围没有被夸大。

## B. 固定 stash 与隔离预演

对含 tracked 改动的普通仓库，先创建**不清理 live 工作区**的 stash 对象：

```sh
S=$(git stash create "sync-preserve-$id")
# 仅在命令成功且 S 非空时执行；失败不进入清理。
git stash store -m "sync-preserve-$id-tracked" "$S"
git rev-parse "$S^1" "$S^2"
```

记录完整 S；读回 S 的工作树树、第二父提交的索引树，分别对照快照中的 Git blob／mode 与索引映射，第一父提交必须是原 HEAD。
S 仅覆盖 tracked 内容，未跟踪内容由 A 的独立快照保护。原始文件字节仍必须保留，不能用经过过滤／换行规范化的 Git blob 代替。
若只有未跟踪内容，`stash create` 可以没有输出；如实记录“无 tracked stash”，不伪造 OID，使用下述未跟踪-only 路径。
不以 `stash@{0}` 作为身份：新 stash 会移动编号；旧 stash 均保留。

建立任务独占、可丢弃的独立临时副本／检出，用固定 L、R 合并，再应用 S 和未跟踪快照进行预演。
临时副本必须能读到 S 及其父树；独立 clone 可显式 fetch 固定 S，不能假设 clone 自动带来 stash 或不可达的索引对象。
它不得共享 live 索引／文件、缓存或运行写回原目录的 hooks；核对需要的仓库规则和过滤语义，无法复制就停止。
用 `git stash apply --index "$S"` 尝试保留暂存关系；检查其退出码、未合并项和内容，不把 apply 成功视为最终语义证明。
未跟踪路径若已由上游占用，先比 blob／原始字节、类型和 mode：完全一致可成为上游文件；不一致保留双版本候选，等待人工决定，不直接覆盖。
有冲突、`--index` 无法恢复或暂存意图不能自动判定时，提供路径、祖先／上游／原索引／原工作区版本及候选差异，**在 live 清理前**请用户决定。
预演不使用临时提交保存秘密。候选文件和完整 diff 只留私有目录，报告不泄露内容。

完成条件：安全候选可重现，暂存与未暂存意图已逐路径核对；或发现冲突并保持 live 原样等待。

## C. 最短清理窗口

只有 A、B 都通过，且入口已验证提交备份分支，才可清理 live；再次核实它仍等于快照。

- 有 tracked 改动：执行 `git stash push --include-untracked -m "sync-preserve-$id-live"`；这会另建 stash 并清理。立即记录新的完整 OID T，验证 T 的 tracked 树等于 S，索引树等于原索引，第三父树覆盖原未跟踪文件及 mode；无未跟踪内容时可没有第三父树。
- T 在清理后才生成，**不能代替清理前已经读回的 S 与外部完整快照**。push 失败、树不一致或工作区未清理完全即停止，不继续 merge；原备份仍保留。
- 只有未跟踪内容：不必制造 stash；在核验快照后逐路径移入任务私有暂存区，记录移动清单，禁止覆盖既有备份。空目录和 stash 未处理的目录元数据也按清单保护；有任何不确定即停。

确认 tracked 索引／工作区清洁、未跟踪碰撞已排除、ignored 内容未变，再回入口执行固定 R 的 merge。
merge 一结束就用已预演的方法恢复：tracked 使用固定 OID 的 `git stash apply --index`，未跟踪从快照逐路径恢复且不覆盖上游；T 的未跟踪树是附加保险，不强行覆盖同名路径。
若 `--index` 在 live 意外失败，不紧接着重复 apply 或无条件换为不带 `--index` 的 apply；先记录部分应用状态并停下，避免叠加修改。
恢复后校验空目录、模式、链接与 ignored 内容；不 pop/drop S、T 或原 stash。
网络等待与耗时验证在恢复后进行；远端再变化时，基于**当前**状态重新快照，不拿旧快照覆盖后续工作。

完成条件：live 已恢复且与预演候选一致，原始版本和所有 stash 仍可读取。

## D. 冲突与暂存语义

冲突必须由人决定；代理只能展示安全候选，不自动选择 ours/theirs：

- 普通 merge 的 ours 是当前 HEAD，theirs 是被合并的提交。
- stash apply 的 ours 是当前合并后的检出，theirs 是 stash 工作内容；其祖先通常是 stash 的原 HEAD，第二父提交才是原索引。不能把同名选项理解为同一种来源。

用户批准后，先在临时副本编辑和验证，再按明确路径应用已批准候选；记录每个路径取舍、双方意图如何保留和内容哈希。
live 如已冲突则保留现场，批准前不自动 abort 或回滚；必须说明实际有哪些文件受影响。
为结束冲突而 `git add -- <paths>` 会改变暂存状态：

- 原来没有 staged 差异时，批准的冲突已解决且索引证据已保存后，可用 `git restore --source=HEAD --staged -- <明确路径>` 把这些恢复内容留为未暂存。它只改指定路径的索引，不改工作文件。
- 原来有 staged 内容时，分别从原索引和原工作树意图构造新索引与工作树；同一路径的部分暂存也必须保持。不能把整文件一股脑 add 或全部取消暂存。
- 普通 merge commit 只含主线提交的合并，不包含恢复的原工作；stash 恢复内容不为“完成同步”而提交。

完成条件：没有未合并项；原暂存意图、未暂存意图均有明确去向，不把解决标记等同于验证通过。

## E. 逐路径语义验收

把每个原变更路径归入以下之一，并比较 blob／原始字节、mode、类型、删除意图及 stage 映射：

| 结果 | 需要的证据 |
| --- | --- |
| 原改动原样保留 | 原索引与工作树两个层次分别与候选一致 |
| 已被新上游包含而变干净 | 上游内容与本地意图一致，原始版本仍在不可变 OID／独立快照中 |
| 双方改动合并 | 双方意图核对、批准记录（有冲突时）、候选哈希和相关验证 |
| 原未跟踪路径变为 tracked | 上游与原内容／mode／类型一致，或已有批准的合并；禁止默默覆盖 |

另核对上游新增内容未被恢复步骤抹掉、原删除／重命名意图仍成立、没有额外文件被暂存、既有 stash OID／顺序未丢失。
例如原有 8 个脏文件中有 4 个已与新上游相同，最终只剩 4 个脏文件可以正确；用文件数相等做验收会误报或掩盖真正丢失。
受影响项目检查通过后，回入口执行祖先检查与推送门。任一证据缺失就报告未验证，不宣称“无损完成”。
